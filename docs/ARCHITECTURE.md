# Архитектура этапа записи

## Контур

1. Browser UI получает список устройств из `GET /api/v1/audio/devices`.
2. `POST /api/v1/recordings` сначала создаёт встречу в bbolt со статусом `starting`.
3. Сервер открывает два нативных аудиопотока: микрофон → `microphone.wav`, системный источник → `system.wav`.
4. После успешного запуска встреча получает статус `recording` и сразу отображается в календаре.
5. `POST /api/v1/recordings/{uid}/stop` останавливает нативные callback, дожидается очереди ScreenCaptureKit и финализирует RIFF/WAVE.
6. Если обнаружено акустическое эхо, WebRTC AEC3 создаёт отдельный `microphone_clean.wav`; исходный микрофонный WAV остаётся неизменным.
7. Silero VAD и выбранная GigaAM v3 E2E RNNT либо Whisper small/medium/large-v3-turbo транскрибируют `microphone.wav`/`microphone_clean.wav` и `system.wav` независимо. GigaAM работает через ONNX Runtime, Whisper — через динамически загружаемую библиотеку whisper.cpp.
8. Если системный транскрипт пуст, ошибочен или вырожден в повторяющуюся фразу, pipeline одним проходом транскрибирует `mixed.wav`; иначе используются два независимых транскрипта.
9. PyAnnote Segmentation обрабатывает системный поток окнами 10 секунд, WeSpeaker извлекает голосовые признаки только из достаточно длинной доминирующей речи без наложений, а кластеризатор Go объединяет локальные дорожки. Одновременно звучащие дорожки имеют жёсткое ограничение cannot-link. Интервалы сопоставляются с фразами по максимальному временному пересечению.
10. В штатном режиме из микрофонного транскрипта удаляются совпадающие по времени и тексту копии системных реплик. Сопоставление учитывает соседние системные сегменты и частично обрезанные гипотезы. В резервном режиме используется только mixed-транскрипт.
11. Фразы сохраняются как транскрипт, после чего выполняется опциональная саммаризация.
12. Pipeline смешивает потоки, при необходимости кодирует общий звук в Ogg/Opus, регистрирует артефакты с SHA-256 и переводит встречу в `completed` или `warning`.

При импорте пользователь явно задаёт роль WAV, Ogg/Opus или MP3. Сервер декодирует файл в PCM16 mono 16 кГц, атомарно заменяет соответствующий канонический источник и создаёт немой парный WAV той же длительности. Для `system` отключается fallback по эквивалентному mixed-потоку, а для `mixed` выполняется ровно один общий проход распознавания и диаризации.

При запуске filesystem reconciler просматривает `data/meetings/YYYY/MM/<uid>`, читает `metadata.json` и фронтматтер текстовых артефактов, после чего восстанавливает отсутствующие записи bbolt. Существующие пользовательские правки имеют приоритет. Если канонические WAV отсутствуют, но зарегистрирован mixed Opus/MP3, pipeline перед ручным повтором декодирует его в `system.wav` и создаёт немой `microphone.wav`; исходный сжатый файл сохраняется.

Браузер не получает доступ к аудиоустройствам и не передаёт PCM через HTTP. Нативный слой компилируется внутрь приложения через CGO:

- Windows — WASAPI capture и WASAPI loopback;
- macOS — CoreAudio и ScreenCaptureKit;
- Linux — PulseAudio/PipeWire monitor с резервным ALSA для микрофона.

Модели, ONNX Runtime и whisper.cpp runtime загружаются отдельно от исходников.
Внешние CLI-процессы для транскрибации и диаризации не запускаются. При
`go run` пути к вручную предоставленным библиотекам задаются в `[inference]`;
ONNX Runtime также можно переопределить переменной `LOCALMEETASSIST_ONNXRUNTIME_PATH`.

Загрузчик использует `.download.part` для докачки. HTTP 416 после получения полного архива трактуется как штатное восстановление: файл проверяется по SHA-256 и передаётся на распаковку. Повреждённый partial удаляется, после чего выполняется один полный запрос без `Range`. На macOS поддерживаются unversioned- и versioned-имена dylib.

Итоговые сегменты транскрипта хранятся отдельным редактируемым слоем в bbolt. Исходные JSON транскрибации и диаризации остаются неизменными. Пакетная правка имён, переносов и объединений спикеров одной транзакцией обновляет встречу, сегменты и карточки Speaker, после чего перестраивается Markdown-транскрипт.

## Диагностика

- основной лог одновременно пишется в stdout и `data/logs/localmeetassist.log`;
- backend и ошибки открытия устройств записываются в основной лог;
- HTTP-запросы логируются с методом, путём, статусом и длительностью;
- UI показывает устройства, предупреждения, пути и последние строки лога.
- раздел «Модели» может загрузить ONNX Runtime и открыть каждую ONNX-сессию без запуска полной обработки;
- настройка саммаризации проверяется коротким реальным запросом с учётом TLS и авторизации.

## Ошибки

Встреча записывается в БД до открытия аудиоустройств. Если микрофон или системный источник не открылся, встреча остаётся в календаре со статусом `failed` и полем `last_error`.

При сбое системного распознавания pipeline сначала пробует общий mixed-поток. Только если недоступны и отдельные, и общий пригодный транскрипт, этап завершается ошибкой. Сбой диаризации не удаляет транскрипт: фразам назначается `SPEAKER_00`, ошибка сохраняется в bbolt как job `diarizing/failed`.

## Эхо от колонок

Запись системного звука остаётся источником истины для удалённых участников. В режиме `audio.echo_cancellation = auto` первые 30 секунд потоков проверяются на корреляцию с учётом задержки, после чего WebRTC AEC3 при необходимости формирует очищенный микрофонный источник для ASR. После двух независимых распознаваний для каждой микрофонной фразы ищутся один или несколько соседних системных сегментов в пределах `echo_time_tolerance_ms`. Совпавшая полная или частично обрезанная эхокопия отбрасывается. Отличающаяся одновременная речь сохраняется, поэтому перебивания не исчезают только из-за пересечения по времени.

## Безопасность

- HTTP слушает только loopback;
- изменяющие запросы требуют случайный session token;
- token запрашивается с `Cache-Control: no-store` и обновляется после рестарта;
- управляемые файлы создаются с правами владельца и удаляются только внутри `data_dir`.
